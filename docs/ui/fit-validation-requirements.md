# Fit 判定 PoC 要件定義書

- ステータス: ドラフト v0.1
- 作成日: 2026-07-05
- 関連文書:
  - `docs/ui/fit-validation-signals.md`（判定シグナル定義 — 本書の確定要件として取り込む）
  - `docs/legal-review-checklist.md`（収集・生成に関する法務論点）
  - `packages/collector`（収集・キャッシュ基盤 — 再利用する）

---

## 1. 背景と検証したい仮説

- **売りたいもの:** エンジニアと企業のミスマッチを防ぐサービス
- **相手:** そのサービスを必要としている企業
- **チャネル:** 問い合わせフォーム経由の営業（フォーム営業）。**送信の自動化は本 PoC ではやらない**
- **検証したい仮説:**

> 公開 Web（HP / 採用ページ / PR / 求人媒体 / 口コミサイト）から取得した情報**だけ**で、
> 「問い合わせする価値がある企業か」を人間の営業判断と同等の精度で見極められる。

この仮説が成立すれば、フォーム営業のターゲットリスト作成を「勘と手作業」から
「根拠（出典 URL）付きの機械判定 + 人間の最終確認」に置き換えられる。

## 2. 検証ゴールと成功基準

### 2-1. ゴール

対象企業リストに対して、シグナル定義（§4）に基づく **need_level（high / medium / low / unknown）** と
その**根拠（シグナル一覧 + 出典 URL）** を出力し、人間の判断と突き合わせて精度を測る。

### 2-2. 成功基準（数値）

| # | 指標 | 目標 | 測り方 |
|---|---|---|---|
| S1 | **人間判定との一致率** | 対象 10 社中 **7 社以上**（70%）で need_level が人間の判定と一致 | §8 の評価手順。high/medium/low の 3 値一致。unknown は分母から除外 |
| S2 | **致命的な取り違えゼロ** | 人間が「逆指標あり・対象外」とした企業を high と判定した件数 **0** | 逆指標（1-5, §4 系）の見落としを個別レビュー |
| S3 | **出典付与率 100%** | high / medium 判定の根拠シグナルすべてに引用 URL がある | 出力 JSON の機械チェック |
| S4 | **unknown 率 30% 以下** | 10 社中 unknown が 3 社以下 | 収集最低要件（§6-3）を満たせた割合。超える場合は収集側の課題として切り分ける |
| S5 | **1 社あたり判定コスト** | 収集〜判定まで人手介入なしで完走し、1 社あたりの実行時間・API コストを記録 | 目標値は設けず**実測して次フェーズの判断材料にする** |

**判定:** S1〜S3 をすべて満たせば仮説は「成立」。S1 のみ未達なら、不一致事例を分析して
シグナル定義（`fit-validation-signals.md`）の改訂 1 回 → 再評価まで許容する。
2 回目でも未達なら「公開情報だけでは不十分」として仮説棄却（人間ハイブリッド前提へピボット）。

## 3. スコープ

### 3-1. やること

1. 対象企業（10 社程度、手動選定）のドメインを入力に、公開 Web から判定材料を収集する
2. 収集した生データから、シグナル定義に沿ってシグナルを抽出する（LLM 利用可）
3. シグナルを集約ルール（§4-2）で need_level に落とし、**根拠付き判定レポート**を出力する
4. 人間の判定と突き合わせ、一致率・不一致理由を記録する

### 3-2. やらないこと（非スコープ）

- **問い合わせフォームの自動送信**（チャネル運用は人間が行う）
- 問い合わせ文面の自動生成（判定に集中する。文面は次フェーズ）
- `docs/product-concept.md` の「リサーチカルテ全機能」（キーパーソン分析・商談準備等）——
  本 PoC は **Fit 判定に必要な範囲のみ**。カルテ機能に引っ張られない
- 対象企業リスト自体の自動発見（リストは人間が用意する）
- UI / ダッシュボード（出力は Markdown / JSON ファイルで十分）
- 認証が必要なサイト・アンチボット回避を要するサイトからの取得

## 4. 判定要件（確定）

### 4-1. シグナル定義

**`docs/ui/fit-validation-signals.md`（ドラフト v0.2）を確定要件として採用する。** 要点:

- **§1 求人シグナル（最優先):** 長期募集（1-1）/ 条件緩和（1-2）/ 大手・子会社の複数募集（1-3, 1-4）は「強い」。自社 careers にエンジニア求人なし（1-5）は「逆指標」
- **§2 口コミ:** エンジニア向けネガティブ口コミ増加（2-1）は「強い」が単体では high にしない
- **§3 経営:** 新サービスリリース（3-1）・採用急拡大（3-2）は「強い」
- **§4 競合・提携:** 同種サービスの自社開発（4-1）・提携（4-2）は「逆指標」＝対象外
- **§5 補助シグナル:** 単体では判定に使わない
- **出典必須:** 引用 URL のないシグナルは判定根拠にしない（→ 根拠不足なら `unknown`）

### 4-2. 集約ルール

signals ドキュメントの「集約の目安」を実装仕様とする:

| need_level | 条件 |
|---|---|
| high | §1 の強いシグナル 1 件以上 かつ 逆指標 0 件 |
| medium | §1 の強い 1 件 + 軽微な逆指標 1 件、または 弱いシグナル 2 件以上 + 逆指標 0 件 |
| low | 弱いシグナルのみ、または逆指標 1 件以上 |
| unknown | 収集最低要件（§6-3）未達、または出典付き根拠の不足 |

ぶれた場合の重み付けは **求人 > 口コミ > 経営 > 補助** の順（signals ドキュメント準拠）。

### 4-3. シグナル定義の変更管理

- PoC 中にシグナル定義を変える場合は `fit-validation-signals.md` を改訂し、バージョンを上げる
- 評価（§8）はどのバージョンで判定したかを記録する（一致率の比較可能性のため）

## 5. 機能要件

パイプラインは 3 段。各段の出力をファイルとして残し、段ごとに単独で再実行できること。

### F1. 収集（collect）

- 入力: 企業ドメイン（+ 分かる場合は求人媒体 URL・口コミページ URL を手動でシード可）
- `packages/collector` を再利用し、対象ソース（§6-1）を取得して生 Markdown + メタデータで保存する
- 既存の `poc-output/<domain>/` 形式（`summary.json` + `contents/*.md`）を踏襲・拡張する
- 取得できなかったソースは「取得失敗」として summary に明記する（silent skip 禁止 — unknown 判定の根拠になる）

### F2. シグナル抽出(extract)

- 入力: F1 の生 Markdown 群
- 出力: シグナル ID（1-1, 2-1, …）ごとに `{ 検出有無, 引用 URL, 根拠となる記述の要約, 確認日 }` を持つ JSON
- LLM（Claude）で抽出してよいが、**引用 URL は収集済みソースの URL に限る**（LLM が出典を捏造しないよう、収集済み URL リストを制約として与える）
- 求人の「掲載期間」（1-1）や「条件変更」（1-2）は時系列データが必要。初回実行時に取れない場合は
  `insufficient_history` として記録し、判定上は「検出なし」と同じ扱いにする（誤検出より欠損を選ぶ）

### F3. 判定・レポート（judge）

- 入力: F2 のシグナル JSON
- §4-2 の集約ルールは **LLM 任せにせずコードで決定的に実装する**（同じ入力 → 同じ判定。評価の再現性のため）
- 出力: §7 の判定レポート（JSON + 人間が読む Markdown）

## 6. 収集要件

### 6-1. データソースと優先度

signals ドキュメントの「収集優先度」を採用する:

| 優先度 | ソース | 使うシグナル | PoC での取得方法 |
|---|---|---|---|
| 1 | 求人媒体（Wantedly, Green, HERP 等） | 1-1〜1-4 | 各社の公開求人ページを collector で取得。**掲載開始日・更新日が取れるものを優先**。robots.txt / 規約で不許可なら取得せず、URL を人間が確認して手動入力可とする |
| 2 | 自社 careers / 採用ページ | 1-5, 1-4, 5-1 | collector（HTML / sitemap） |
| 3 | PR / ニュース | 3-1, 3-2, 4-1, 4-2 | collector（RSS / news-sitemap — 既存実装で実績あり） |
| 4 | 転職口コミ（OpenWork 等） | 2-1 | **規約上スクレイピング不可の可能性が高い。** 自動取得は行わず、PoC では人間が確認した内容を手動入力するインターフェース（JSON 手書きで可）を用意する |
| 5 | HP（会社概要・事業） | 4-1, 4-2 | collector（既存実績あり） |

### 6-2. 収集マナー（既存方針の継続）

- robots.txt 尊重・不許可なら取得しない、`Crawl-delay` 優先
- 同一ドメイン 10〜20 秒の不均一間隔・同時接続 1 本（`poc-output` の manners 設定を踏襲）
- 全取得を fetch_log に記録（`legal_basis` 含む）
- 認証回避・アンチボット回避はしない。取れないサイトは「取得不可」として扱う

### 6-3. 収集の最低要件（unknown の線引き）

1 社あたり以下がそろわなければ need_level は `unknown`:

1. 自社 careers の有無確認（確認した URL の記録を含む）
2. 求人媒体の求人情報 1 件以上（自動 or 手動入力）
3. PR / ニュース 1 件以上

## 7. 出力要件（判定レポート）

1 社につき機械可読 JSON と人間可読 Markdown を出力する。

```jsonc
// poc-output/<domain>/fit-judgement.json（イメージ）
{
  "company": { "name": "...", "domain": "..." },
  "judgedAt": "2026-07-05T...",
  "signalsVersion": "v0.2",          // fit-validation-signals.md のバージョン
  "needLevel": "high",               // high | medium | low | unknown
  "signals": [
    {
      "id": "1-1",
      "detected": true,
      "strength": "strong",          // strong | weak | counter
      "evidence": [
        { "url": "https://...", "quoteSummary": "...", "checkedAt": "2026-07-05" }
      ]
    }
  ],
  "counterSignals": ["4-2"],
  "missingData": ["2-1"],            // 取得できなかった/履歴不足のシグナル
  "rationale": "求人シグナル 1-1（6ヶ月以上の継続募集）を検出。逆指標なし。"
}
```

Markdown 版は「判定 / 主根拠（出典リンク付き）/ 逆指標 / 取得できなかった情報」を 1 画面で読める分量にする
（フォーム営業前に人間が 1〜2 分で妥当性確認できること）。

## 8. 評価方法

1. **対象企業の選定:** 10 社。high 見込み・low 見込み・逆指標持ち（競合提携等）が混ざるように人間が選ぶ
   （全部 high 見込みだと一致率が意味を持たないため）
2. **人間側の正解づけ:** システム実行**前に**、人間（営業判断者）が同じ公開情報を見て need_level を付ける。
   ブラインドにする（システム出力を見てから正解を付けない）
3. **突き合わせ:** need_level の一致 / 不一致、不一致の場合は「収集漏れ / 抽出ミス / 集約ルールの問題 /
   人間側の判断根拠が非公開情報だった」のどれかに分類して記録する
4. **記録先:** `docs/ui/fit-validation-results.md`（評価実施時に作成）に、企業別の判定・正解・不一致理由・
   signalsVersion・実行コスト（S5）を残す

「人間側の判断根拠が非公開情報だった」件数は仮説の限界を示す最重要データなので必ず分類する。

## 9. コンプライアンス要件

- `docs/legal-review-checklist.md` の現行 PoC 方針を継続する（商用化前の弁護士確認事項はそちらに集約）
- 本 PoC は社内検証・無償段階であり、収集は情報解析目的の中間コピーとして整理（著作権法 30 条の 4 想定）
- 口コミサイト（OpenWork 等）・求人媒体は**利用規約でスクレイピングを禁止している可能性が高い**。
  §6-1 のとおり、規約 NG が疑われるソースは自動収集せず人間の目視 + 手動入力に倒す
- 判定レポートに口コミを引用する場合は逐語転載せず要約 + リンク参照とする
- 収集対象企業からの停止要請には収集を止められること（既存 collector の対象管理で対応）

## 10. 既存資産との関係

| 資産 | 扱い |
|---|---|
| `packages/collector` | **再利用する。** robots/manners/fetch_log/キャッシュはそのまま。求人媒体向けの取得先追加は adapters の範囲で行う |
| `poc-output/`（ローカル収集サンプル） | 開発・評価用サンプル。出力フォーマット（summary.json + contents/）の踏襲元 |
| `docs/product-concept.md` | 参照はするが**要件の根拠にしない**。リサーチカルテ全機能は本 PoC の非スコープ |
| `docs/ui/fit-validation-signals.md` | 本書 §4 の確定要件。改訂はバージョン管理する |
