# プロダクトコンセプト: 営業ターゲット深掘りリサーチエンジン（仮称）

- ステータス: ドラフト v0.1
- 作成日: 2026-07-04
- 経緯: 初期壁打ちセッションでの議論をもとに整理

---

## 1. サービス概要

**一言で:** 優秀な営業アシスタントが訪問前に 1 社 1 時間かけて行うリサーチを、
すべてのターゲット企業に対して自動でやってくれる Web アプリケーション。

ユーザー（BtoB 営業担当者）が営業先の企業リストを持ち込むと、1 社ごとに
**「リサーチカルテ」** — 事業の現状、攻め筋の仮説、メッセージに使える具体的な文脈 —
を自動生成する。カルテを見ながら人間がアプローチするだけで価値が成立し、
将来的にはフォーム送信・メール等のアクション自動化へ拡張する。

### ポジショニング

営業支援プロダクトは 3 層に分解できる:

| 層 | 内容 | 競合状況 |
|---|---|---|
| データ収集層 | 企業・人物の属性データベース | ZoomInfo / Apollo / FORCAS / Musubu が巨大な moat。量では勝てない |
| **分析・エンリッチ層** | **個社の深掘りリサーチ、攻め筋仮説、パーソナライズ素材** | **海外は Clay が急成長、国内は空白地帯 ← ここに参入** |
| アクション層 | フォーム送信 / メール / LinkedIn 自動化 | 規約・法務リスクが高い。既存プレイヤーは「テンプレ大量送信」で嫌われている |

本プロダクトは**分析・エンリッチ層にくさびを打つ**。属性データ（業種・規模・所在地）を
売るのではなく、既存ツールのユーザーが毎回手作業でやっている「そこから先の個社リサーチ」を売る。

### 突く競合の弱み

- **FORCAS / Musubu（国内 DB 型）**: 属性データ止まりで、個社の深掘りと文脈生成がない
- **GeAIne 等（国内フォーム営業）**: 送信はできるがリサーチが浅く、テンプレ感が強い
- **Clay（海外）**: 近い価値を提供するが、日本語ソース（PR TIMES・登記・国内求人媒体）と
  日本語文面の品質が弱く、操作も複雑で国内 SMB には重い

## 2. ターゲット

**一次ターゲット: 国内の BtoB 営業チーム**（SMB〜ミッドマーケットの新規開拓・インサイドセールス）

### ユーザー像とペイン

- リスト（属性データ）は持っているが、個社リサーチは 1 社 30〜60 分の手作業
- リサーチを省くとテンプレ営業になり、返信率が下がる。丁寧にやると件数がこなせない
- 「今この会社に売れる理由」を毎回自力でひねり出している

### 二次ターゲット（将来）

- 営業代行・SalesOps 会社（ヘビーユース、高単価、濃いフィードバック源）

### 国内市場を選ぶ理由

- 海外ツールは日本企業データ・日本語品質が弱く、参入障壁として機能する
- フォーム営業文化があり、LinkedIn 依存度が低い（= LinkedIn 規約リスクを避けた設計と整合する）

## 3. 提供価値: リサーチカルテ

1 社ごとに生成するカルテの構成（MVP 時点の想定）:

1. **事業サマリー** — 事業概要、最近の動き（プレスリリース、ニュース、決算、採用動向）
2. **攻め筋の仮説** — 「この会社は今◯◯に投資しているため、△△の課題を持つ可能性が高い」
3. **刺さる文脈（フック）** — メッセージに使える具体的な話題（「先日の◯◯の発表を拝見し…」）
4. **キーパーソン候補** — 役職、登壇歴、note / X での発信などの公開情報
5. **競合利用状況** — 導入技術、既存ベンダーの痕跡
6. **パーソナライズ文面案** — カルテを踏まえた、コピペで使えるアプローチ文面
7. **出典リンク** — すべての記述に情報源を付与（ハルシネーション対策 + 信頼性）

## 4. コア機能（MVP スコープ）

### 方針

**「リスト持ち込み → オンデマンドでカルテ生成」を最小 MVP とする。**
リスト生成機能を持たないことで DB 大手と戦わず、事前バッチではなくオンデマンド生成に
することでデータ基盤の作り込みを後回しにし、コア価値（リサーチ品質）の検証に最短で到達する。

### MVP に含む

| # | 機能 | 内容 |
|---|---|---|
| 1 | 企業リスト取り込み | CSV / 企業名・URL の直接入力 |
| 2 | リサーチカルテ生成 | LLM エージェントが公開 Web を収集・分析し、上記 3 章の構成で生成 |
| 3 | カルテ閲覧 UI | 1 社ずつ閲覧、出典リンク付き |
| 4 | 文面案の生成とコピー | 自社プロダクト情報（ユーザーが登録）× カルテでパーソナライズ |
| 5 | エクスポート | CSV / Markdown コピー |

### MVP に含まない（将来ロードマップ）

- リスト生成・ターゲティング検索（DB 大手の土俵）
- シグナル検知の常時監視（資金調達・求人・役員交代の通知）← Phase 2 候補
- フォーム自動送信・メールシーケンス ← Phase 3。「送っていい相手にだけ質の高いものを送る」設計で参入
- LinkedIn 連携 ← 規約違反リスクが高く、国内優先度も低い。**当面やらない**
- CRM 連携（Salesforce / HubSpot）

## 5. データソース戦略

MVP は**公開 Web のオンデマンド収集のみ**で始める。

| ソース | 用途 | 取得方法（想定） |
|---|---|---|
| 企業公式サイト | 事業概要、ニュース、採用ページ | クロール |
| PR TIMES 等プレスリリース | 最近の動き、攻め筋の根拠 | クロール / 検索 |
| 求人媒体・採用ページ | 投資領域・組織課題の推定 | クロール |
| EDINET / 決算資料 | 上場企業の財務・戦略 | 公式 API |
| ニュース検索 | 直近トピック | 検索 API 経由 |
| X / note 等の発信 | キーパーソンのフック | クロール（公開情報のみ） |
| 官報・登記 | 資金調達・役員変更（Phase 2 のシグナル検知で本格化） | 将来 |

**注意事項:**

- robots.txt・各サイト利用規約の尊重をクローラー実装の要件とする
- 個人に関する情報は公開ビジネス情報（役職・登壇・公開発信）に限定し、
  個人情報保護法上の整理を Phase 2 前に行う

## 6. 技術方針（データ収集）

### クローラー選定

**MVP から Crawl4AI を採用する（決定）。**

- OSS・無料で、LLM 向けの Markdown 抽出が優秀。Playwright ベースで JS レンダリングにも対応
- 従量課金の外部 API に依存せず、取得ロジックを最初から自社でコントロールできる
- Python 製のため、TypeScript の本体とは分離した**クローラーマイクロサービス**として実装する
  - 本体（TS）→ HTTP（FastAPI 等）→ Crawl4AI サービス、という構成
  - インターフェースは「URL（+ 抽出指示）→ Markdown / 構造化 JSON」に絞り、本体からは実装を隠蔽する

検討した代替案（参考・不採用）:

| 候補 | 特徴 | 不採用の理由 |
|---|---|---|
| Firecrawl | マネージド API。Node SDK あり、TS 本体から直接呼べる | 従量課金の外部依存になる。Crawl4AI で内製する方針のため |
| Crawlee | Apify 製、TypeScript ネイティブ。Playwright 統合 | LLM 向け Markdown 抽出が自前実装になる |
| Jina Reader | URL→Markdown の単機能 API。手軽 | 細かい制御が効かない |

### その他

- 本体: TypeScript (strict) / Node (ESM) / pnpm（ワークスペース既定方針に従う）
- 分析・生成: Claude API（リサーチエージェント + カルテ生成）。全記述に出典を紐づける
- カルテはオンデマンド生成。レイテンシ対策として生成中の進捗表示とキャッシュを設計に含める

## 7. リスクと制約

| リスク | 対応方針 |
|---|---|
| LinkedIn 自動化の規約違反 | **スコープから除外**（アカウント BAN・プラットフォーム排除リスク） |
| フォーム自動送信のレピュテーション / 「営業お断り」問題 | Phase 3 まで延期。参入時は「お断り検知 + 少量高品質」を設計原則に |
| スクレイピングの規約・法務 | robots.txt 尊重、個人データは公開ビジネス情報に限定、Phase 2 前に法務整理 |
| LLM のハルシネーション | カルテ全記述に出典リンク必須。出典のない推測は「仮説」として明示 |
| LLM コストとレイテンシ | オンデマンド + キャッシュ。1 カルテあたりの原価を計測し価格設計に反映 |
| リサーチ品質が刺さらない | 開発前に手動検証（下記 8 章）で品質基準を先に確立する |

## 8. 検証計画（開発前にやること）

コア価値は「攻め筋仮説が実際に刺さるか」。**コードを書く前に**検証する:

1. 手動 + Claude で実在企業 10 社分のリサーチカルテを作成する
2. 現役の BtoB 営業担当者に見せ、「これを見て営業したいか / いくらなら払うか」をヒアリング
3. 刺さったカルテ・刺さらなかったカルテの差分から、品質基準とプロンプト設計の要件を抽出

**MVP 後の成功指標（候補）:** カルテ利用時の返信率改善、1 社あたりリサーチ時間の削減、
「カルテなしには戻れない」と答えるユーザー比率。

---

## 9. ロードマップ

- **Phase 1（MVP）**: リスト持ち込み → リサーチカルテ生成 → 文面案（本ドキュメントのスコープ）
- **Phase 2**: シグナル検知 — 登録企業の常時監視と「今売れるタイミング」通知。データパイプラインの本格化
- **Phase 3**: アクション層 — フォーム送信 / メールシーケンス。「送っていい相手にだけ、質の高いものを」
- 継続検討: CRM 連携、営業代行向けの API / 大量処理プラン
